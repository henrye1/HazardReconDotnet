What this app does

The credit engine says which accounts defaulted and how they moved between rating buckets. This app takes the engine's own debug output and reconciles it against the two records the business actually keeps — the write-off file and the IFRS9 exposure file — so you can answer two questions before the numbers are signed off:

rule
Check 1 — can every default be traced? A default the engine booked should show up as a write-off, or in the IFRS9 population, or both. One that appears in neither is untraced: the model recorded a loss that has no downstream record.
swap_horiz
Check 2 — the reverse: written off, never flagged? An account that was written off, was scored by the engine, and yet never entered the default bucket. The ones written off inside the scoring window are the real exceptions — the engine had the account in front of it and did not call it.
fact_check
And a third, silent one: does the matrix reconcile? The migration matrix is rebuilt from the scored accounts and compared cell-for-cell against the engine's own accumulated arrays in debug.json. It either passes, or you are told which cells disagree.

Each run can cover up to four sets — typically the same portfolio at different reporting dates or scenario strengths — and every set is checked independently, then written into one workbook and one dashboard.

Column mapping only the write-off and exposure files are mapped

The engine's own files (lgd_defaults.csv, pd_scored.csv, debug.json) have fixed column names and are read as they are. Your two files are the ones that vary, so they are mapped:

FileFieldNeededWhat happens without it
Write-offLoan account number Required The join key — check 1 traces every default through it, so the file cannot be loaded without one.
AmountOptional Write-off exposure comes out as zero.
Report dateOptional Check 2 cannot say whether a write-off was pre-, in- or post-window; everything reads as undated.
Customer idOptional Carried into the exception CSV only; nothing matches on it.
Exposure (IFRS9)Loan account number Required The join key for the IFRS9 side of check 1.
Amount outstandingOptional Exposure per account is left empty.

Each field is resolved in order: an exact header match, then a mapping you saved before for a file with the same set of columns, then an AI guess with a confidence score, and failing all three it is left unmapped. Every field is editable whichever way it was filled, and Reset to suggestions undoes your edits.

Reading the two checks
Check 1 — default traceability

Every default in lgd_defaults.csv is looked up, by normalised account number, in the write-off file and in the IFRS9 file. Each one ends up labelled Write-off + IFRS9, Write-off, IFRS9 or UNTRACED. The trace rate is traced ÷ total defaults. Alongside the count you get the exposure carried by the untraced ones, which is usually the number that decides whether they matter. Untraced accounts already marked fully recovered are called out separately — they are typically benign.

Check 2 — written off but never defaulted

Accounts in the write-off file that the engine scored but never put in the default bucket. Each is classified against the engine's scoring window as PRE-WINDOW, IN WINDOW, POST-WINDOW or UNDATED. Only the in-window ones are true exceptions — a pre-window write-off happened before the engine was looking, and a post-window one after. The last bucket each in-window account was scored in is shown too: a cluster in bucket 4 usually means the hazard rates are too soft at the top of the book rather than that any single account is wrong.

Both checks are per set, and every exception is exported to CSV so you can work the list outside the browser.

Reading the migration matrix

Rebuilt from pd_scored.csv, one row per account-month. Rows are the bucket moved from, columns the bucket moved to, buckets 1–6. The diagonal is accounts that stayed put; everything off it moved.

Cells count movements, not accounts — one account scored across twelve months contributes twelve movements, so the totals are larger than your account count and should be. Use the month selector to slice a single period, and Row % to read a cell as "the chance of moving from this row's bucket to that column's bucket" (each row sums to 100%).

Bucket 0 is missing on purpose. Bucket 0 is default, and default is check 1's territory, not a migration.

The all-months matrix is validated cell-for-cell against CohortNlambda in debug.json. PASS means the rebuild agrees with the engine exactly. FAIL reports the largest disagreeing cell and is worth chasing — it means the scored file and the engine's own accumulator tell different stories. N/A just means debug.json carried no matrix to compare against.

What the run stages mean steps 2–7 repeat for every set
Read the analysis folders Work out which uploaded file is playing which role.
Load inputs Read the write-off, defaults, scored and IFRS9 files for the set.
Check 1Trace each default to the write-off or IFRS9 file.
Migration matrix Rebuild the rating migrations from the scored file.
Check 2 Find write-offs inside the scoring window that never defaulted.
Validate migrations Compare the rebuilt matrix against the engine's own.
Write CSVs Export the traced, untraced and migration detail for the set.
Build the workbookWrite every set into one Excel file.
Generate AI analysis Ask the model to explain the reconciliation. Skipped when no model was chosen.
Render the dashboard Build the interactive migration matrix and engine results.
Write the analysis memo Turn the analysis into a Word document. Skipped when no model was chosen.

A stage finishes as done, skipped (an optional step with nothing to do), warn (it finished, but something was missing or did not reconcile — the run carries on) or error. A warn is worth opening the log for; it is how a missing pd_scored.csv or a failed matrix validation announces itself.

AI analysis and asking about a run

AI is entirely optional. Leave the model on Skip and the reconciliation, dashboard, workbook and CSVs are all produced exactly as they otherwise would be — you simply get no written analysis and no memo. If the model is unreachable mid-run the run still completes; the analysis is dropped, not the reconciliation.

shield
What is sent to the model Aggregates only: per-set counts and totals, the trace rate, the check 2 window split, the distinct-account counts, the 6×6 migration matrix and the engine's parameters. No account numbers, no customer ids, no account-level rows ever leave the server for analysis or chat.
forum
Ask about this run Available on a completed run. It sees the same aggregates, so it can explain a number or compare sets, but it genuinely cannot tell you about one account. A run that had analysis is answered by the same model that wrote its memo, so the two can never contradict each other; a run that skipped analysis lets you pick a model for the conversation. Enter sends, Shift+Enter starts a new line.
visibility
The one exception: column mapping When a column cannot be matched by its header or from a saved mapping, the header row and up to five sample rows of that file are sent so the model can guess. Those are real data rows. An exact header match or a saved mapping never reaches the model.

When something goes wrong
help
"Check 2 skipped" The set had no write-off file, or no scored population. Add the write-off file, or include pd_scored.csv in the debug upload, and run again.
help
Almost everything is untraced Usually the write-off file is missing, or its account-number column is mapped to the wrong field. Open step 2 and check the join key on both the write-off and exposure files before reading anything into the trace rate.
help
Migration validation says FAIL The matrix rebuilt from pd_scored.csv disagrees with the engine's own accumulated arrays. Most often the scored file and the debug.json came from different engine runs. Check they are from the same debug.zip.
help
The run says Interrupted The server restarted while it was working. Nothing is corrupted — open the run and choose Run again, as long as the inputs are still within their 30 days.
help
A set is refused as too large The limit is per set, not per file. Upload the extracted lgd_defaults.csv, pd_scored.csv and debug.json instead of a large debug.zip, or split the reporting dates across separate runs.
help
Chat or analysis is unavailable The model gateway is not configured on this deployment, or the run was reconciled without a model and none has been chosen for the conversation. Everything except the written analysis works regardless.
help
"Your session expired" Sign in again. A run already on the server keeps going without you and will be waiting on My runs.
